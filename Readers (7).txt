
Grouping Transactions by Account

Question

We are building the backend for a banking compliance monitoring system. When a transaction occurs on any account, the system records it. Each transaction has properties mentioned below. One account can have many transactions.

Definitions:

A "Transaction" is one financial event recorded by the system. It has an ID, an account ID, an amount, a transaction type (DEPOSIT, WITHDRAWAL, or TRANSFER), and a timestamp (in minutes since the start of the day).
A "ComplianceMonitor" is the class used to manage all transactions for the day.

To begin with, two tasks:

1) Read through and understand the code below. Take as much time as you need, and feel free to run the code.
2) The test for ComplianceMonitor is not passing due to a bug in the code. Make the necessary changes to ComplianceMonitor to fix the bug.


Suspicious Transaction Reversals

Question

Compliance teams need to detect suspicious transaction reversals — deposits followed by withdrawals of the same amount within a short time window.

1) Implement get_suspicious_reversals(time_window). It returns a list of (account_id, deposit_transaction_id, withdrawal_transaction_id) tuples representing suspicious reversal pairs.

A DEPOSIT and WITHDRAWAL form a suspicious reversal when:

They belong to the same account.
They have exactly the same amount.
The withdrawal timestamp minus the deposit timestamp is greater than 0 and less than or equal to time_window.
Each transaction may appear in at most one pair.
Process each account's transactions in timestamp order, not insertion order. When multiple unmatched deposits qualify for a withdrawal, pair with the earliest.

Please discuss your approach before implementing.


Structuring Detection

Question

High-value transactions catch the obvious cases, but some activity is deliberately structured to avoid those checks. Compliance teams need to detect "structuring" -- a pattern where someone splits a large incoming transaction into multiple smaller ones to avoid triggering the reporting threshold.

For each account, examine its transactions in timestamp order and identify any time window where:

Only DEPOSIT and TRANSFER transactions are included.
Each included transaction has an amount strictly below individual_threshold.
The sum of the included transactions meets or exceeds combined_threshold.
The difference between the earliest and latest included transaction timestamps is less than or equal to time_window.
WITHDRAWAL transactions are not included in the sum and break the current sequence. Transactions with amounts greater than or equal to individual_threshold are not eligible and terminate the current sequence. Transactions occurring before and after either type of sequence-breaking transaction cannot be combined in the same window.

1) Implement detect_structuring(individual_threshold, combined_threshold, time_window). It returns a list of account IDs for accounts where structuring is detected, sorted in ascending order. If no accounts are flagged, return an empty list.

Please discuss your approach before implementing.
